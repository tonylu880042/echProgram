3. Differences Between idea.txt and the Current App (record only; no code changes)
------------------------------------------------------------
idea.txt proposes 22 Programs/experiences; the current App library implements only 8 items:
- Hero: FAT_BURN, GLUTE_BLAST, VERTICAL, SURPRISE_ME.
- Supporting: EASY_STROLL, SPEED_DEMON, ROLLING_HILLS, HEART_HEALTH.
The current detail catalog provides only FAT_BURN; the other visible items enter an unavailable state. `MainActivity` is still wired to `NoOpWorkoutSessionStarter`, so Start only proves the setup/validated boundary and does not create a real workout session.
Known duration conflict (client decision required): the current App FAT_BURN hero tile displays `45 MIN`, and the current FAT_BURN detail default is also `45 MIN`; the detailed FAT BURN draft in idea.txt is `30 MIN`. The current App GLUTE_BLAST hero tile displays `20 MIN`, while its current detail is not available; the detailed GLUTE BLAST draft in idea.txt is `30 MIN`. The client must decide whether the current App, idea.txt, or a new launch spec is the single source of truth, then align the tile, detail, profile, and selectable durations.
Gate3A already provides a FitOS read-only telemetry boundary, but Gate3B speed/incline control, command ACK, pause/resume, safe stop, and real session reconciliation are not yet available. HR, history/persistence, and the generator are also not implemented.
These txt files do not imply that the above gaps have been fixed. The next code increment should first establish one ProgramDefinition source and completeness tests against these specifications.

4. Shared Client Decisions Across Programs
------------------------------------------------------------
1. Units: Should the UI default to MPH or KM/H? Should speed, distance, and history comparisons be stored in a fixed canonical unit?
2. Machine capability: What are the maximum speed/incline, step size, ramp rate, and support for 0% and 15%+ on each launch model?
3. Naming: Which names and external copy for FAT BURN, BOOTY BURN, 12-3-30, VERTICAL MILE, RECOVERY, and related terms receive legal/marketing approval?
4. AIDL control: What are the ACK, timeout, rejection reason, pause/resume, Binder death, host restart, safety-key, and app-crash behaviors for start/stop/speed/incline?
5. HR: Which Apple Watch and other HR monitor paths are supported? What is the authoritative target-zone source, HR LOST timeout, hysteresis, and control authorization?
6. Estimated calories/elevation: What are the data sources, formulas, confidence, rounding, `ESTIMATED` caveat, and whether FitOS may report an authoritative value?
7. Persistence: What are the data and privacy/deletion policies for profile, user cap, manual override, Adapt preference, history, PR, generator seed, and generator version?
8. Safety/UX: What common UI copy and default safe behavior apply to no device, stale data, clamp, control failure, and user-initiated stop?

5. Recommended Confirmation Order and MVP Groups
------------------------------------------------------------
Batch 1: Confirm units, machine caps/limits, and common safety/preview copy. Use read-only/static profiles to complete detail/profile previews for FAT BURN, GLUTE BLAST, POWER WALK, ROLLING HILLS, RECOVERY WALK, QUICK 10, SWEAT 30, PYRAMID, SUMMIT, BOOTY BURN 15, HIIT 20, SPEED LAB, WALK + RUN, ENDURANCE, and ECHELON HYBRID RUN.
Batch 2: After the control contract is approved, connect the fixed-profile session engine; implement countdown, NEXT, manual override, stale/clamp handling first, without enabling unvalidated automatic control.
Batch 3: After the HR contract is confirmed, build ZONE 2; after the elevation authority/formula is confirmed, build VERTICAL; after the calories estimator/time limit is confirmed, build CALORIE TARGET.
Batch 4: Build ECHELON CHALLENGE after sufficient history exists; build the 5K READY progression after its baseline/cycle decisions; build SURPRISE ME after the deterministic generator contract is approved.
Batch 5: Complete persistence, the results screen, evidence rules for comparisons/PRs, and client/legal copy before deciding which Programs may enable real device control.
